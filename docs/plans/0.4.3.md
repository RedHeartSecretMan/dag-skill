# DAG 0.4.3 优化方案

状态：已批准，实施与验证进行中。基线为 `16445a12e4557bba24f0bfc5cd70523207e444ed`。本文保留本次批准范围与验收方式；执行规则以[当前协议](../../skill/dag/SKILL.md)为准，发布单独记录。

版本目标：让 Coordinator 能明确判断整个 DAG 是否完成、发现缺口后继续正确的责任路径，并减少重复探索和调度歧义。保留 Coordinator Agent 与 Execution Agent 两种角色、两种 Integration Transition，以及现有 Runtime Skill、CLI 和 Definition Index 契约。

## 范围与优先级

| 工作包 | 本次目标 | 当前依据与判断 |
| --- | --- | --- |
| A：完成判定与返修 | 覆盖全部批准义务，核对最终交付的证据适用性，将关闭后的缺陷交回明确责任票。 | [Complete 条件](../../skill/dag/SKILL.md#resume-safely-and-finish)与 [DAG Revision 影响审计](../../skill/dag/references/definition-binding.md#complete-a-dag-definition-checkpoint)已有主体；普通后续产品变化和已验收票返修需要更明确的规则。核心范围。 |
| B：未知操作结果恢复 | 外部动作中断后先回读归属与结果，再决定是否重试。 | [操作交付](../../skill/dag/references/ticket-execution.md#gather-zero-diff-evidence)已要求实际结果；调用成功但响应或落盘丢失的窗口需要补齐。核心范围。 |
| C：并行补位消歧 | 新派发或恢复的任务与既有 live claims 一起检查。 | [调度规则](../../skill/dag/SKILL.md#compute-and-claim-the-runnable-frontier)已有独立性、资源隔离和容量约束；本项明确其检查集合，属于消歧。 |
| D：可选共享探索笔记 | 复用昂贵的搜索和定位，保持关键事实核验及小上下文。 | [研究笔记](../research/shared-exploration-notes.md)支持小幅补充；没有当前 DAG 的定量性能结论。 |

四项均纳入 0.4.3。实施时先完成 A、B，再加入 C、D。共享笔记属于运行时可选能力，不成为每次执行的固定前置阶段。

## A：完成判定与返修

### 批准义务必须有归属

启动重建、Definition 变更以及报告 Complete 前，核对当前 governing Spec 中每项范围内的验收义务：它应由有效 Ticket 承担，或由项目已有的 whole-DAG gate 及明确责任人承担。已有 Ticket、Spec、gate 定义和收据指针足够时，直接使用它们。

发现遗漏时，记录具体义务与缺失归属，由 Coordinator 按已有权限和 DAG Revision 规则处理。义务覆盖检查关注“谁负责交付什么”；测试设计仍由 Execution Agent 在实现时发现，不恢复 claim 前的穷举 acceptance-to-probe 表。

### 最终交付需要当前仍适用的证据

后续候选涉及共享接口、配置、依赖或已有交付行为时，在该 Ticket 的既有验证与审查中识别可能受影响的已验收义务。Coordinator 检查这些影响是否已有处置，保持实现和审查责任在 Execution Agent 内。

最终覆盖与影响核对绑定最终 Definition 及当前 Accepted Integration Tip 的 commit/tree，链接已有报告。旧证据保留其真实 Base、候选、输入和环境身份。只有相关行为、输入、验证定义与环境仍适用且有影响核对依据时，才能支持最终完成结论；实际受影响或项目要求绑定新候选的检查重新执行。最终 whole-DAG gates 使用最终 Accepted Integration Tip，或项目允许且明确证明适用性的原证据；不得把旧执行结果标记成在新 tip 上运行。

区分“尚需核查适用性”和“已证明义务不满足”。无关 Base 前进不自动重开全部 Accepted Tickets，也不触发全量重测。未解决的缺陷或证据缺口阻止 Complete，并进入其现有责任路径。

这是历史 Ticket 证据对最终交付的适用性核对；新候选仍遵循现有 gate 有效性与 fresh review 契约，旧 Candidate Review Record 不改绑到新 tip。

### 已验收票可以沿原责任路径修复

对于已确认缺陷，先定位当前有效义务的责任票。在仍进行的本票范围内修复时继续现有工程循环；责任票已关闭时，Coordinator 按项目既有状态规则和授权重开、恢复 claim，并以当前 Accepted Integration Tip 分配 Ticket Base。只有责任、范围、依赖或批准语义确实需要调整时，才进入 DAG Revision。

保留历史验收和证据，继续从现有集成结果向前修复。重用可用工作区；若旧工作区已依规则回收，从当前 Base 建立工作区并保留旧证据指针。继续执行仍需一个可写 owner，替换 Agent 前沿用已有存活性确认。返修候选经过正常 gates、fresh review 和串行 promotion。

按实际受影响的输出、输入身份与义务核查消费者。暂停依赖失效输出的工作，保留其 ownership 与 WIP；仅重审或重开确实受影响的已验收消费者。前置票重开期间，新 claim 与依赖输出的最终验收仍须满足 Accepted direct inputs 的要求；这与是否撤销已验收消费者的当前结论分别判断。无关分支继续推进。规则不足以决定归属或 tracker 状态时，提出准确的待决事项，不自行发明字段映射。

将现有稳定 tracker 更新规则扩展到返修带来的验收处置：项目要求入历史的状态或证据变化继续通过 DAG Definition Checkpoint；selected path 变化仍重绑 Definition Index 并做完整影响审计。所需逐票更新完成后，才重新 claim 并分配该 checkpoint 后的当前 Base；显式批处理规则仅允许其规定的独立工作继续。最终覆盖核对在最后一个必要 checkpoint 后确认当前 tip，或补充合格的等价与影响审计。不在活跃 Integration Transition 中改写冻结证据。

重开处置在没有活跃 Integration Transition 时记录。与 pending candidate 无关的新发现可排队处理；实证推翻候选或其证据的新发现遵守[现有冻结与恢复规则](../../skill/dag/references/integration-transitions.md#reconcile-the-local-integration-ref)，不能为结束 Transition 而先 Accepted。本项补齐已验收票返修，不扩展为所有 CAS 后异常的自动恢复方案。

## B：未知操作结果恢复

范围限定为零差异操作 Ticket 中已获授权、可能产生重复副作用的外部动作。在调用前将 Ticket、目标、artifact 或必要参数身份、已有授权及可用的查询或幂等关联信息保存到 off-delivery recovery store。复用 [Run Receipt 的 outstanding work](../../skill/dag/references/integration-transitions.md#run-receipt-and-frozen-evidence)，敏感参数使用安全引用。响应后及时补充原生操作 ID、实际结果和回读证据。集成分支同步继续遵循其既有恢复协议。

中断恢复、超时或响应丢失后，先用动作所属系统的查询能力核对：

- 确认是原请求且仍运行：接续观察该操作；确认完成：复用并核验其结果。
- 有充分证据证明未发生副作用，或已有原生幂等机制能安全恢复：在原授权范围内继续。
- 无法唯一关联、查无结果但可能尚未可见、或查询失败：保留未决事实，继续可用的核查；需要选择或外部条件时沿用现有决策与阻塞规则。

不以“没有收到成功响应”推导“没有执行”。服务不支持可靠关联或幂等时，不承诺恰好执行一次；该限制必须体现在下一步选择中。实现范围是恢复契约，不增加通用外部操作引擎。

## C：并行补位消歧

每次 claim、resume 或补入新票时，交付独立性、资源隔离和容量检查覆盖本次候选与既有 live claims，并计入下游 Runtime Skill Agents 的实际资源需求。等待最终处理的票按其真实占用检查，不仅依据票数推断宿主容量。

例如 A、B 正在并行，A 验收后解锁 C：即使当前 Frontier 只有 C，仍需检查 C 与运行中的 B。C 与 B 冲突时，可以继续运行满足条件的 D。保持并行实现与定点验证、串行最终处理和集成的既有策略。

## D：可选共享探索笔记

多个 Ticket 会重复调查同一问题时，允许 Coordinator 或当前责任人在已有范围内安排探索。派发仅提供相关问题、读取条件和笔记指针，继续采用零历史或最小相关历史。

笔记通常包含问题与适用票、来源定位和版本、已确认事实与假设、影响适用性的条件。消费者核对影响实现或验收的关键事实；相关源码、配置、依赖或环境变化后只刷新受影响结论。笔记缺失或冲突时回查权威来源。

每份完成版本由一个作者维护，确认实际消费宿主可访问，并按现有资源清单保留或清理。笔记本身不授予产品决策、依赖或验收权威；正式研究 Ticket 的交付物继续按其契约验收和保留。具体案例与取舍沿用[共享探索研究](../research/shared-exploration-notes.md)，正式协议只保留改变执行行为的短条款。

## 验收方案

| 场景 | 必须观察到的行为 |
| --- | --- |
| Spec 有三项义务，但 Tickets 与既有 gates 只覆盖两项 | 给出准确的遗漏及责任决定；不报告 Complete，不自行扩大批准范围。 |
| 后票改变配置，破坏前票已验收行为 | 识别具体义务与受影响证据，修复或重新验证；不能只凭旧 PASS 收口。 |
| 后票只影响无关区域 | 保留旧证据的原身份，按影响依据复用；不机械重开或重跑全部票。 |
| 所有 claims 已关闭后，最终 gate 失败 | 恢复明确责任票的单写者与当前 Base，完成正常返修和 fresh review。 |
| 返修需要更新 Git-tracked tracker，且存在相关与无关消费者 | 正确完成所需 checkpoint；处理受影响消费者并保留现场，无关工作可继续。 |
| 外部操作已产生效果，但响应丢失；首次查询又暂未显示结果 | 先关联回读，不因暂时查无记录重复执行；无法确认时报告具体缺失条件。 |
| A 完成后补入 C，而 B 仍运行并与 C 争用设备 | 将 B 纳入检查，延后冲突任务，允许其他独立票补位。 |
| 多票共享笔记，随后部分来源改变或与 Spec 冲突 | 按当前权威来源核查受影响结论；不会让笔记成为新契约或验收证据。 |
| 可选笔记跨宿主不可读，或待清理文件其实是正式研究输出 | 前者回退原始来源；后者按正式交付和证据保留规则处理。 |

验证分三层记录，避免把不同证据混为一谈：

1. **协议审查。** 对上述场景做独立审读，检查能否从文档唯一推出下一步、责任人和停止条件；审查新增规则与 claim、tracker、冻结证据规则的交叉影响。
2. **隔离 Agent 演练。** 在临时 Git 项目中实际执行关闭后返修与并行补位；使用本地可记录副作用的模拟服务验证“动作完成但响应丢失”的恢复。记录候选身份、工具调用、操作次数及恢复结果。场景推演不能替代已运行的演练，未运行部分单独列出。
3. **仓库检查。** 沿用 [CI](../../.github/workflows/ci.yml) 的完整测试、Python 3.12/3.14 矩阵、Ruff、Markdown 和 helper 入口检查；补查受影响文档的本地链接、锚点、复制包可达性与盘古之白。测试聚焦可观察行为，避免增加整句协议文本匹配。

共享笔记先验证正确性和可选回退；可以记录搜索路径复用情况，但不以尚未测量的 token 或耗时下降作为本版本承诺。

## 交付顺序

1. 完成 A、B 的协议增量及对应场景验证，先消除收口、返修与恢复歧义。
2. 加入 C、D，复核其与既有 ownership、上下文隔离、资源管理的关系。
3. 同步用户文档并做整体精简，运行验证，给出最终差异与未覆盖范围。
4. 按后续发布指令合入和发布 `v0.4.3`，核对远端提交、tag 与 CI。保留 `v0.4.2` 身份；根据实际 tag 差异整理发布说明，避免将此前已发布的调度能力重复列为新增。

审核重点是四项范围及上述行为边界。实现时复用已有契约；若演练发现必须改变公共格式、权限边界或角色结构，先回到方案审查。
