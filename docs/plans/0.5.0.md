# DAG 0.5.0 并行执行与上下文效率方案

状态：仓库内 0.5.0 实现完成；基线为 `f015a3b`（当前 `main` 与 `origin/main` 一致）。外部 Agent Host、Target Project tracker 和真实运行性能 qualification 需要在具体 DAG 上单独验证。本实现保持现有运行协议。

本轮复查补充了四条硬约束：新增记录只能是既有 Run Receipt 的索引或派生视图；只读 review 可以继续并行，唯一强制串行的是 Integration Transition 及其相邻的 acceptance / tracker 变更；释放运行时资源不能释放 Ticket writer、workspace、唯一 WIP 或 evidence 所有权；缓存、摘要和指标都不能替代权威输入与原始证据。

## 结论

下一轮优化的主线应是“先建立可观测的控制平面，再压缩上下文，最后扩大安全并行度”。当前系统已经具备两种角色、零历史派发、可选共享探索笔记、运行时资源检查、Ticket Base 和串行 Integration Transition。继续直接增加 Agent 数量，收益会先被以下成本抵消：

- Coordinator 在每次 claim、resume、handoff 和 acceptance 时重复阅读完整协议和全局状态。
- Ticket 的当前状态、候选身份、门禁证据和资源占用主要通过自然语言交接，难以只传递变化部分。
- 实现和只读 review 可以并行，但 current-tip 检查、Base refresh、tracker checkpoint 和 promotion 共同形成一个容易排队的串行段。
- Runtime Skill 的下游 Agent 由 Execution Agent 内部启动，当前调度层只能保守估算其容量，无法解释等待和过载。
- Accepted Integration Tip 前进后，仍在工作的 Ticket 可能产生 stale Base，导致重新应用、重跑门禁和 fresh review；这些返工成本目前没有计量。
- 共享探索笔记已有读取条件和来源指针，但还没有统一的缓存身份、失效规则和消费记录。

因此目标不是让每个 Ticket 都拥有更多上下文或更多 Agent，而是让每个阶段只获得完成当前决策所需的最小上下文，并让 Coordinator 能根据真实资源和等待原因调度。

## 当前实施状态

本仓库已完成 P0～P4 的结构化运行记录、上下文压缩、缓存、并行 admission、claim CAS、review 绑定、恢复、Promotion CAS、Ticket disposition 和 Terminal Outcome audit。新增状态均保留在既有 off-delivery Run Receipt / artifact 体系中，没有新增第二事实源。

P0 已把 dispatch、handoff、tool output、phase、resource、wait 和 rework 的标准 measurement names 放入 `Execution Checkpoint`，并要求记录 `measurement_version`、`observed_at` 和可比较的数值单位。宿主暂时无法提供真实 token 计数时，记录可复现的字节或字符估算，并把估算标记在运行证据中。

P1 已提供 `skill/dag/scripts/record_execution_checkpoint.py`、`skill/dag/scripts/index_execution_record.py` 和 [execution-records reference](../../skill/dag/references/execution-records.md)。前者校验 Capsule、Checkpoint、Evidence Index、资源声明、上下文 metrics、claim generation、Ticket Base、scope 和 artifact digest，并以 create-once、原子、off-delivery 的 shadow record 发布；后者在 Coordinator 提供 Receipt digest 和 generation 后重新验证全部引用并以 CAS 写入 `execution_records`。两者都不改变 claim、Git ref、Integration Transition 或 acceptance。

真实运行记录消费和性能结论属于外部 qualification：需要具体 Agent Host、Target Project、tracker 规则和可比 DAG 基线，不能由本仓库静态测试替代。

## 当前系统的优势和瓶颈

### 已经做对的部分

1. Coordinator Agent 和 Execution Agent 的责任边界清楚。实现、测试、candidate 和 review finding 闭环在 Ticket 内完成，图状态、acceptance、promotion 和 successor unlocking 由 Coordinator 负责。
2. `zero-history` 或最小相关历史派发已经避免把整个 DAG 的聊天记录复制给每个 Execution Agent。
3. Ticket Base、Candidate Review Record、DAG Definition 和 Integration Transition 都有精确身份，能够阻止旧证据被误当成当前证据。
4. 并行检查已同时考虑交付独立性、运行时隔离和容量，并允许在已有 live claim 旁补位。
5. 共享探索笔记被定义为 advisory context，不授予产品、依赖或 acceptance 权威；这为缓存探索成本提供了安全的入口。

### 第一瓶颈：协议上下文的固定成本过大

每次派发都要求 Agent 阅读完整执行协议，Coordinator 还要在多个生命周期节点重读多个 reference。该规则有利于正确性，但把“必须知道的少数约束”和“只有特定分支才需要的规则”混在同一上下文层级中。

建议把上下文拆成四层：

| 层级 | 内容 | 使用时机 |
| --- | --- | --- |
| C0：Ticket Capsule | Ticket 身份、Base、直接依赖、范围、义务、gate、workspace、权限、finalization policy | 每次派发和恢复，必须携带 |
| C1：协议索引 | 当前阶段的规则章节、命令入口、失败分类、证据字段 | 进入实现、review、promotion 或 recovery 分支时携带 |
| C2：权威输入 | Ticket、Spec、源码、配置、依赖和历史证据的精确指针及短摘录 | Agent 按任务读取，避免复制整份文件 |
| C3：运行产物 | 测试输出、review 报告、日志和中间文件的 artifact handle | 需要诊断或验收时按需加载 |

C0 应该足够小且结构稳定。C1 只告诉 Agent 去哪里读取规则，不把所有规则正文再次复制到每个 prompt。C2 和 C3 使用内容身份、路径、命令和摘要引用；大输出放在 workspace 或 off-delivery evidence store 中。

### 第二瓶颈：自然语言交接没有 delta 语义

当前交接能表达正确事实，但难以区分“新事实”和“上一次已经说过的事实”。下一步应把交接改为固定的 `Execution Checkpoint`：

```text
ticket_id, owner, workspace, base
phase: explore | implement | verify | review | promotion | blocked
changed_paths[]
accepted_inputs[]
candidate: commit, tree, range
evidence_delta[]
open_findings[]
resource_claims[]
next_action
blocking_condition
```

它是 Run Receipt 的一个索引化子结构，不是新的 acceptance 权威。Execution Agent 产生候选 Checkpoint artifact，Coordinator 验证 owner、claim generation、Base、candidate 和 evidence identity 后，才把它写入 Run Receipt。Run Receipt 由单一 Coordinator 串行更新，并使用 generation / compare-and-swap 防止旧 Checkpoint 覆盖新状态；写入应先落盘、校验 digest，再原子替换当前索引。完整报告和日志仍由原始 artifact 保留，Checkpoint 只保存身份、状态、变化和下一动作。恢复时读取最后一个已验证 Checkpoint 加上 delta，不重放整个 Agent 历史。

### 第三瓶颈：实现并行，最终化串行

当前“completion priority”已经避免多个 Agent 同时进入最终化，但它把实现、final gates、review、tracker checkpoint 和 promotion 的不同资源混在一个优先级上。结果可能是：一个 Ticket 在等待远端或外部操作时继续占据执行容量，另一个本可以完成的 Ticket 只能等待。

建议将执行模型显式分成两个调度 lane，并把 review 从强制串行段中排除：

- **Build / Review lane**：探索、实现、局部测试、candidate-specific final gates 和针对固定 candidate 的只读 review。满足独立性和资源隔离时尽量并行。
- **Promotion lane**：current-tip 再确认、Base refresh、Integration Transition、必要 tracker checkpoint 和 semantic acceptance。每个时刻只允许一个 Ticket 进入这一段；Agent 可以在 Build / Review lane 保留 WIP，但必须释放可回收的运行时资源。

Integration Transition 仍然严格串行。Promotion lane 不是新的 Agent 角色，而是 Coordinator 对已有 Execution Agent 的 phase 和资源预约；这样不会复制 review 或 acceptance 责任。只读 review 是否并行，仍由现有的独立性、运行时隔离和容量检查决定，不因为存在 Promotion lane 而被不必要地串行化。

优先级不应只按先完成先处理，而应综合：

1. 能否解锁关键后继或减少 DAG critical path。
2. 当前候选离 Promotion 的剩余工作量。
3. 该 Ticket 持有的不可共享资源是否应尽快释放。
4. 等待时间是否已达到 aging 阈值，避免低扇出 Ticket 永久饥饿。
5. Promotion 期间发生 Base refresh 的预期返工风险。

不应在没有实测数据时引入复杂的最优调度算法。第一版只需要明确 phase、资源 reservation、等待原因和简单的 critical-path / aging 规则。

### 第四瓶颈：容量和返工成本不可见

当前容量规则正确地要求计入 Runtime Skill 的内部 Agent，但它没有统一的资源描述。每个 claim 至少应声明：

```text
agent_slots
runtime_skill_slots
cpu_weight, memory_weight
gpu_ids or device class
ports, databases, run directories
exclusive paths or shared interfaces
```

Coordinator 只在 reservation 成功后 claim。资源描述不需要精确预测模型 token；先覆盖会导致错误并行的外部资源和内部 Agent 数量。宿主无法确认容量时，不把未知当作可用，回退到可验证的串行执行，并记录 `capacity_unknown`。

同时记录以下返工原因：`base_stale`、`evidence_invalidated`、`review_finding`、`external_wait`、`capacity_wait`、`writer_recovery`。没有这些原因，无法判断增加并行度是在缩短关键路径，还是在增加 stale candidate 和重复门禁。

## 目标运行结构

建议保持现有两角色和两种 Integration Transition，只在既有 Run Receipt 上增加四种轻量索引对象。它们不是新的调度数据库、Acceptance Obligation 来源或 evidence 来源；Git-backed Definition、Coordinator 的语义决定、Execution Agent 的原始产物和 Run Receipt 的现有所有权仍保持不变。

### 1. Run Manifest 视图

Run Manifest 是 Run Receipt 的紧凑派生视图，记录 run identity、Definition identity、Accepted Integration Tip、publication mode、live claims、phase、resource reservations、frontier 摘要和 pending transition 指针。它不复制 Ticket 正文、review 正文或日志，也不替代 Git 和原始证据。视图无法从 Run Receipt 重建或 digest 不一致时，视图失效，Coordinator 回到既有恢复流程，不根据残缺视图继续推进。

### 2. Ticket Capsule

Ticket Capsule 是一次 dispatch 的不可变输入快照，绑定 Ticket、直接输入、Ticket Base、workspace、scope、Acceptance Obligation、required gates、权限和 finalization policy 的权威指针与 content identity。可以携带小的规范化字段以减少读取，但必须同时保存来源 path、commit / tree、digest 和 generation；不得把过期的复制文本当作当前义务。Ticket Base、Definition、Scope、Obligation 或 authority 改变时生成新 Capsule，旧 Capsule 只保留 provenance。

### 3. Evidence Index

Evidence Index 只保存每项 evidence 的类型、producer、命令或操作、commit / tree、环境身份、artifact path、digest、适用范围和 invalidation reason。它可以记录 `observed_result`，但不能单独产生 `Accepted`、`Superseded` 或 gate applicability 结论。Coordinator 先读索引决定是否需要加载正文；验收时仍回读原始证据和 Git 身份。缺少原始 artifact、digest 或 producer identity 时，索引只能标记 evidence unavailable。

### 4. Exploration Cache

共享探索笔记增加统一身份：`question`、`scope`、`source identities`、`target tree or Definition identity`、`environment`、`author`、`created_at` 和 invalidation conditions。`valid_until` 只能作为提醒，不能证明内容仍然有效；源码、配置、依赖、环境、Definition 或目标 Ticket 输入的 identity 变化才是失效判断的依据。笔记正文采用“结论、证据指针、限制、待核验事实”四段格式。

消费笔记的 Agent 必须记录消费的 note identity，并重新核验影响实现或 acceptance 的关键事实。笔记由一个 writer 通过临时文件、边界检查、digest 校验和原子替换发布；未完成或冲突版本不可见。源码、配置、依赖、环境、Definition 或 Ticket 输入 identity 改变时，只能在完成影响审计后保留未受影响结论。笔记缺失、冲突或失效时回到权威来源，不能把缓存当成批准计划。

## Token / context 优化策略

### 派发阶段

- 默认只发送 C0 Ticket Capsule、C1 协议索引和 C2 指针，不继承 Coordinator 全历史。
- 恢复时发送上一个 Checkpoint 加 delta；不要把所有旧 tool output 拼回 prompt。
- 将相同的 Spec、项目规则和 Runtime Skill 版本变成 host 可复用的只读引用。若宿主不支持引用或 prompt cache，则保留指针方案，不假设存在缓存能力。
- 对每个 Ticket 标注 `context_budget`，预算用于 dispatch payload、tool output retained bytes 和 handoff summary。预算是观测和告警，不是为了截断验收义务。
- `context_budget` 不能截断 Acceptance Obligation、权限、Base / candidate identity、未知操作结果、review finding 或外部 block 的 closing condition；若权威输入不可访问，应报告 context / authority gap，不得用摘要补齐。

### 工具输出阶段

每次工具调用返回三部分：短状态、结构化身份、artifact handle。artifact 必须先写入授权的 off-delivery 或 workspace 路径，拒绝越界路径、符号链接和不安全替换，再计算 digest；handle、digest 或原始结果缺失时，证据不可用。默认只保留短状态和身份；失败诊断或 acceptance 再按 handle 读取正文。结构化身份至少包括命令、cwd、exit code、duration、stdout / stderr artifact、commit / tree 和 digest。

禁止把完整测试日志、完整 diff、重复的源码片段和完整 review 报告复制到多次交接中。摘要必须保留失败测试名、首个关键错误、受影响路径和可追溯 artifact，不以“测试失败”这种不可执行的摘要替代证据。

### Runtime Skill 阶段

Runtime Skill Bundle 在 run startup 验证一次，Ticket invocation 复用该事实。Execution Agent 只向 `$code-review` 传固定 Base、candidate range、changed paths、Spec 指针、Acceptance Obligation 和 tracker workflow；reviewer 通过指针按需读取，而不是接收整个 DAG 上下文。

同一 Ticket 内的 TDD、final gates 和 review 共享 `Evidence Index`，但每个结果仍保留自己的 producer、环境和适用范围。这样可以减少重复命令和重复摘要，同时不会把不同门禁的结果错误合并。

### 上下文压缩的安全边界

压缩只能删除已被身份化且可重新读取的内容。以下内容不能只保留模型生成摘要：Acceptance Obligation 原文、权限和授权边界、Ticket Base 与 candidate identity、失败操作的未知结果、review finding 原文及 disposition、外部 block 的 closing condition。

压缩后的恢复必须通过 Checkpoint identity、artifact digest 和权威输入回读验证。若摘要与权威来源冲突，以权威来源为准，并把冲突记录为 evidence gap 或 Coordinator decision。

## 并行调度方案

### Admission

每次 claim / resume 先生成候选 reservation，再检查：

1. Hard Dependency 和 Accepted direct inputs。
2. changed-path / shared-interface 冲突。
3. 端口、设备、数据库、目录和运行时隔离。
4. Execution Agent 和 Runtime Skill 的嵌套容量。
5. 当前 Build / Review lane 和 Promotion lane 的占用。

检查结果记录为可执行的 `admission_reason`，例如 `accepted`、`path_conflict`、`gpu_capacity`、`promotion_lane_busy`。不要只记录“不能并行”，否则无法优化。

### Work conservation

Promotion lane 忙时，其他独立 Ticket 可继续 Build / Review lane；某个 Ticket 等待外部操作时，只能释放已经确认 quiescent 的可共享运行时 reservation。不得释放 write-capable Agent、workspace、唯一 WIP、evidence、外部操作关联记录或 claim ownership。若 writer liveness 不确定，沿用现有恢复规则保留 claim 和资源，不派发第二个 writer；等待不变成 Execution Outcome。

### Base refresh

Promotion 前由 Coordinator 冻结 current Accepted Integration Tip。发现 stale Base 时，只让原 owner 在原 workspace 继续 refresh；不重新派发第二个 writer。刷新前后分别记录 candidate、gate 和 review identities，测量一次 Base refresh 造成的实际新增工作量。

### Promotion batching

当多个候选已经完成 Build / Review lane，可按一个短批次依次进入 Promotion lane，但每个候选仍单独完成当前协议要求的 current-tip 检查、CAS、publication、tracker checkpoint 和 acceptance。批次只减少 Coordinator 的重复 frontier 重算，不合并 Ticket 义务、gate 或 review 结果。

### 故障边界

| 故障 | 处理 | 禁止的推断 |
| --- | --- | --- |
| Checkpoint 的 claim generation、Base 或 candidate 与当前 Run Receipt 不一致 | 丢弃该 Checkpoint 作为当前状态，回读现有 claim 和 workspace，再由原 owner 继续或按 writer-liveness 规则恢复 | 不能把旧 Checkpoint 覆盖当前状态，也不能据此派发替代 writer |
| 资源 lease 过期、进程是否存活未知或外部操作仍可能占用资源 | 保留 claim、workspace、write-capable Agent 和关联记录，建立具名 recheck event | 不能用超时、无响应或资源暂时空闲推断 writer 已停止 |
| artifact handle 不存在、路径越界、符号链接变化或 digest 不匹配 | 标记 evidence unavailable，停止依赖该 evidence 的 review / promotion，保留原始现场等待恢复 | 不能用摘要、exit code 或“文件曾经存在”代替原始 evidence |
| Exploration Cache 的 source identity、目标 tree 或 Definition identity 改变 | 使受影响笔记失效，回查权威输入；未受影响部分只有完成影响审计后才能继续使用 | 不能用 `valid_until` 或作者声明证明内容仍然适用 |
| Agent Host 不支持真实 token、只读引用或 artifact 读取 | 记录 capability gap，使用可验证的最小指针或串行路径；该 run 不进入不可比的性能结论 | 不能假设 prompt cache、跨 Agent 文件可见性或隐含的上下文持久化 |
| Coordinator 在 Promotion / Integration Transition 中断 | 保留冻结 transition record、evidence 和本地 ref，按既有 Integration Recovery 读取并对账 | 不能重新生成候选、改变 Base、重复远端操作或先标记 Accepted |

## 分阶段路线

### P0：先测量，再优化协议

在不改变 acceptance 语义的前提下，记录：

- 每次 dispatch / resume / handoff 的输入字符数或 token 估算。
- 每次 tool output 的原始大小、保留大小和重复读取次数。
- 每个 Ticket 的 Build、Review、Promotion、Integration、external wait 和 capacity wait 时长。
- 并发 Agent 数、Runtime Skill Agent 数、资源 reservation 和实际冲突。
- `base_stale`、重复 gate、review finding、恢复和未知操作结果的次数。
- 从 claim 到 Accepted 的总 token 估算、墙钟时间和关键路径时间。

如果宿主没有真实 token 计数，先记录 prompt / artifact 的字节数和可复现的字符估算，并明确标记为 estimate；不同 tokenizer 的估算不能混合比较，也不能把估算冒充账单数据。指标记录本身放在 off-delivery，失败时不能影响现有 acceptance。

### P1：Ticket Capsule + Checkpoint + Evidence Index

先实现纯数据结构和序列化 / 校验，不改变调度决策。让现有 prose handoff 同时生成结构化索引，使用结构化索引恢复；连续几个真实 run 验证“恢复不需要重放全历史”。当前已完成 shadow write 和 Receipt CAS indexer；灰度阶段结构化记录只做 shadow write，缺失时不阻断原协议，但该 run 不得进入性能结论；结构化记录成为恢复或调度输入后，校验失败必须停止对应优化路径并回到既有权威恢复流程，不能静默使用旧摘要。

验收重点：错误 Base、旧 candidate、缺失 evidence、重复 Ticket claim、未知操作结果都必须 fail closed；结构化记录缺失时不能静默降级为“看起来完成”。

### P2：按需上下文和探索缓存

将协议按阶段建立 C1 索引，把大工具输出改为 artifact handle；为共享探索笔记补充身份、失效和消费记录。探索笔记与 Artifact Handle 契约已经完成；下一步把真实 handoff 的输出采集接到 handle，再选择确实存在重复探索的一个 run 做对照，比较重复读取量和关键事实回查次数。

验收重点：缓存失效后能回到权威来源；缓存不可用不会阻塞独立 Ticket；正式研究交付物仍按 Ticket obligation 保留。

### P3：双 lane 调度和资源 reservation

phase、wait reason 和 resource reservation 已由 Checkpoint schema 承载，admission planner 与 claim CAS 已实现冲突、容量、Promotion lane 和 live claim 记录。下一步把真实 Coordinator resume / writer-liveness 现场接到 request 与 claim bundle，并在成功 CAS 前重新读取 live frontier。初版只使用简单优先级：已测量的 critical-path、unblocker、资源释放和 aging；缺少历史时使用稳定的依赖扇出和先到先服务，不能伪造精确剩余工时。

验收重点：并发提升不能带来 duplicate writer、错误共享资源、错误 Base promotion、证据误绑或 Stalled 误判；所有 reservation 失败都能解释原因。

### P4：候选和 review 成本优化

Review Context Capsule、Candidate Review Record、handoff / Promotion verifier、writer recovery、Promotion Evidence Package、Ticket disposition CAS 和 Terminal Outcome audit 已实现，并已接入低层 local CAS promotion helper；在不跳过 fresh review 的前提下复用探索上下文、changed-path 分析、Artifact Handle 和 Evidence Index，减少 reviewer 重新定位资料的成本。候选 bytes、Base、tree、range、commit list 或 obligation 改变时产生新的 context key 和 Candidate Review Record。实现完成后的外部 qualification 顺序是：在真实 Target Project 上生成并消费 Run Receipt 记录，按项目 tracker 规则执行 checkpoint，运行 `$code-review` 与 Promotion，最后验证 Complete / Stalled 和性能基线。

验收重点：旧 review 只能作为 provenance；任何新 candidate 都不能只凭旧 PASS 推广。

## 验收指标

并行优化的成功标准应同时看吞吐、上下文和正确性。每个指标都要绑定 run、Ticket、Base 和 measurement version，避免把不同协议版本的结果混在一起：

| 指标 | 目标方向 | 失败信号 |
| --- | --- | --- |
| DAG critical-path wall time | 下降 | 总 Agent 数上升但关键路径不变 |
| 每个 Accepted Ticket 的 dispatch / handoff tokens | 下降 | 依赖完整历史才能恢复 |
| 重复探索和重复工具输出比例 | 下降 | 同一问题被多个 Agent 从头调查 |
| Promotion lane 等待时间 | 下降 | candidate 完成后长期排队 |
| Base refresh / stale candidate 比例 | 下降 | 并行越多返工越多 |
| 资源 reservation 失败可解释率 | 100% | 只返回笼统 capacity failure |
| duplicate writer、错误 promotion、错误证据绑定 | 0 | 任一发生即阻断优化发布 |
| context truncation 导致的义务遗漏 | 0 | 任何压缩后 acceptance 语义丢失 |

不能只看总 token。总 token 下降但 stale Base、review finding 或验收等待上升，说明优化把成本推迟了。也不能只看 wall-clock；需要同时保留每个 Accepted Ticket 的证据完整性和恢复可重建性。

性能结论采用同一类 DAG 和相近 Agent Host 的历史基线与影子记录比较。P0 先确认指标可以从现有运行证据重建，再决定是否启用 P2 / P3；没有可比基线时只报告观测结果，不宣称收益。任何 duplicate writer、错误 promotion、错误 evidence binding、丢失未知操作结果或 context compression 造成的义务遗漏，都立即停止优化策略并保留完整恢复材料。

## 明确不建议的方向

- 不先引入第三种常驻 Agent 角色或独立 scheduler service；当前瓶颈首先是状态和证据不可观测。
- 不把完整 DAG、Run Receipt 或其他 Ticket 的聊天历史广播给所有 Agent。
- 不把共享探索笔记升级为计划、依赖或 acceptance 的第二权威。
- 不因为“节省 token”而跳过 fresh candidate review、Base 身份校验、未知操作结果核对或最终适用性审计。
- 不以固定 Agent 数量代表容量；Runtime Skill 的嵌套 Agent、设备和外部资源必须计入 reservation。
- 不在没有 P0 数据时承诺固定百分比的加速或 token 节省。

最值得先做的具体增量是 P0 + P1：为现有两角色协议加上 `Ticket Capsule`、`Execution Checkpoint` 和 `Evidence Index`，先把每次交接的重复内容和 stale Base 返工量测出来。它们能直接验证后续 P2 / P3 是否值得实施，并且不改变当前 Git、review、acceptance 和恢复契约。P1 的实现顺序已经完成 schema、owner / generation 校验、shadow write、Receipt CAS index 和恢复重建的工具契约；下一阶段只需在真实运行中验证消费路径，再进入 P2。
