# DAG Skill Design

This document explains the stable design choices behind the DAG Skill. [`SKILL.md`](../skill/dag/SKILL.md) is the normative entrypoint; the branch-specific references it requires carry the detailed runtime contract, and [`CONTEXT.md`](../CONTEXT.md) is the shared glossary. The Git-backed Target Project's live instructions, any Specs, Tickets, tracker, repository, and acceptance rules remain authoritative for an actual run.

## Objective

The scheduler should make graph decisions, not manage a Ticket's internal engineering loop. A Ticket should keep moving while its objective, Accepted inputs, and Acceptance Obligation remain stable, even when it needs several implementation, test, Promotion Candidate, and review rounds.

The smallest architecture that preserves those boundaries is:

```text
thin Coordinator Agent
`-- end-to-end Execution Agent for one Ticket
    |-- tdd and codebase-design when applicable
    `-- code-review
```

This design exposes only graph-relevant outcomes to the Coordinator Agent. Test failures and ordinary review findings stay with the Ticket owner; acceptance and successor unlocking stay with the graph owner.

Context isolation follows the same ownership split. The Coordinator Agent holds the whole-DAG state, while each Execution Agent starts from an explicit Ticket contract and the assigned live workspace rather than inherited Coordinator history. The Agent Host uses zero-history dispatch when available, otherwise its smallest history window. The contract carries applicable user and project constraints, including those for downstream Agents, and pointers to existing approvals. This preserves explicit requirements without bringing unrelated Tickets, Run Receipt state, or prior tool output into the Ticket implementation context.

## Why there is no DAG Review Agent

`code-review` already defines its own review process. Repeating that process in the DAG contract would create two sources of truth, split finding ownership, and add lifecycle states without producing better evidence.

The Execution Agent therefore invokes `code-review` and closes its in-scope findings. The Coordinator Agent receives the complete result exactly as returned, wrapped by a Candidate Review Record that binds the fixed Ticket Base, candidate commit/tree, and evaluated range. The wrapper matters because the review output itself does not need to repeat Git identities. A dismissal is valid only when its disposition carries stronger project evidence; a supported blocking finding cannot pass merely because it was labeled “handled.”

## State and ownership

Only one role may mutate each state surface at a time:

| State surface | Owner |
| --- | --- |
| Effective graph, claims, blockers, Runnable Frontier, acceptance | Coordinator Agent |
| DAG Definition binding and DAG Definition Checkpoints | Coordinator Agent |
| One Ticket workspace, implementation, gates, candidates, finding closure | Execution Agent |
| Review judgment for a fixed candidate | `code-review` |
| Integration Transition serialization and successor unlocking | Coordinator Agent |

One claim has one write-capable Execution Agent. A replacement is safe only after the previous writer has observably stopped and the existing workspace and evidence are handed over. This is an ownership invariant, not an assumption based on elapsed time.

## DAG Definition binding

A Git-backed DAG should not depend silently on an untracked local plan, an available external service, or an off-delivery selector. Before the first claim, the Coordinator Agent binds the governing Spec, effective Tickets, Hard Dependencies, and Acceptance Obligations to the accepted integration history. In-repository definitions enter as tracked files; an external tracker enters through a normalized snapshot containing complete governing content and source provenance. A single discoverable **DAG Definition Index** makes the effective Approved DAG unambiguous even when the repository contains several plans. The normative path, schema, equivalence, and object-mode rules live in [`references/definition-binding.md`](../skill/dag/references/definition-binding.md) and are enforced against one exact commit by the bundled validator. Binding creates no commit only when Starting Base on a new run, or the current Accepted Integration Tip later, already contains the exact Definition and an equivalent validated index; unsafe or unfaithful persistence requires an explicit decision.

This is one deep Coordinator Agent interface: bind the DAG Definition and return the verified Accepted Integration Tip that future Tickets use as Ticket Base. The validator hides path normalization, targeted Git object inspection, schema, and identity checks behind one read-only command; it queries the index and selected paths without enumerating the full commit tree. Artifact discovery, snapshots, checkpoint review, and publication remain implementation details. The Execution Agent receives the same Ticket, Accepted inputs, Ticket Base, workspace, and authority pointers as before, so plan publication does not enlarge the Ticket-local context.

Run state is a different surface. Claims, Agent and worktree identities, liveness, pending synchronization, and the Run Receipt stay in an off-delivery recovery store. The receipt records the DAG Definition Index and bound identities for recovery but is not their source of truth. Before local compare-and-swap it also freezes a pending Integration Transition's candidate-bound review and gate identities; for a DAG Definition Checkpoint it additionally freezes every acceptance-impact disposition and its audit identity. A path that mixes definition and run state is not admitted wholesale; the Target Project splits it or supplies a normalized definition snapshot. Missing split or snapshot rules require one explicit classification or layout decision rather than an invented projection. Stable tracker or prior acceptance evidence is optional DAG Definition Checkpoint content only when the Target Project requires that audit trail. The DAG Definition Checkpoint's own completion record stays off-delivery, avoiding a commit that recursively changes the identity it describes.

When the Target Project requires stable Ticket state or acceptance evidence to be written back to a Git-tracked tracker, the project rule must say when to write it and how Accepted, Superseded, PASS, FAIL, and BLOCKED become tracker status, checklist, verdict, and evidence fields. The DAG adds no tracker schema or second state authority. The Coordinator finishes the current acceptance or Integration Transition, records any still-required update in the Run Receipt, and then uses the existing DAG Definition Checkpoint path. A state/evidence-only checkpoint may change only unselected stable audit paths; changing an indexed Definition input requires an updated index and the complete Definition and acceptance-impact audit. A checkpoint that already contains the exact required update satisfies it once. A per-Ticket rule blocks successor unlocking and another claim until completion; an explicitly batched rule may remain outstanding during graph-independent work but must complete before a Definition revision or Terminal Outcome. Missing field rules remain Coordinator-owned unresolved decisions rather than inferred tracker edits.

The Run Receipt is also the compare source for the local DAG Integration Branch ref. A new run creates that ref only from an exact **Starting Base** selected by Target Project rules, an explicit user instruction, or existing accepted integration evidence. Starting Base is pre-publication identity: when binding needs no new bytes it may become the first Accepted Integration Tip after the selected Integration Publication Mode completes; otherwise it remains the recorded Starting Base for the first Integration Transition, and the reviewed DAG Definition Checkpoint becomes the first Accepted Integration Tip. On resume without an in-flight Integration Transition, the ref must equal Starting Base before that first acceptance and the recorded Accepted Integration Tip afterward. With a persisted Integration Transition, the ref may equal its Base, meaning the compare-and-swap has not happened, or its candidate commit, meaning local promotion happened and only Integration Transition completion or remote synchronization remains. Recovery reuses the exact frozen evidence. Before compare-and-swap, changed evidence requires explicit cancellation and a new Integration Transition; after compare-and-swap, replacement is impossible. Any other SHA or incomplete Integration Transition identity is drift; the Coordinator Agent preserves it and requests reconciliation instead of silently adopting or overwriting it.

When binding requires new bytes, the Coordinator Agent creates an isolated DAG Definition Checkpoint from Starting Base on a new run or from the current Accepted Integration Tip later. It checks graph identity and acyclicity, reference and scope integrity, sensitive data, and the Target Project's applicable documentation gates, then obtains a fresh independent Standards/Spec review. Product tests are not an automatic metadata gate. The Coordinator Agent closes DAG Definition Checkpoint-local findings; every byte change invalidates the old gates and review. The DAG Definition Checkpoint uses the same serialized compare-and-swap and remote reconciliation as a Promotion Candidate; after required readback it becomes the downstream Ticket Base but accepts no Ticket and creates no DAG Milestone.

An approved DAG Definition change later in the run uses the same DAG Definition Checkpoint. It waits for any active Integration Transition and must land before affected work starts or resumes. Unaffected active work may finish first; affected claims and workspaces are preserved and paused. Only a DAG Definition Checkpoint changes the DAG Definition Index, bound definition path set, or content identities: every Promotion Candidate preserves all three and excludes transient run state. If Ticket scope genuinely requires a DAG Definition change, the Coordinator Agent completes that DAG Definition Checkpoint first and only then refreshes the same Ticket onto the resulting Accepted Integration Tip as its new Ticket Base. Transient run-state changes never create a DAG Definition Checkpoint, which keeps the normal Ticket loop and its latency unchanged.

A DAG Revision also has an acceptance impact. For every Accepted Ticket or Superseded Ticket affected directly or through the governing Spec, evidence bound to the previous DAG Definition is stale unless a fresh audit proves it still satisfies the new identity, scope, Hard Dependencies, and Acceptance Obligation. Otherwise the approved DAG Revision must use Target Project rules to reopen that Ticket or assign the obligation to an effective replacement; unclear transition rules create a Coordinator-owned unresolved decision and keep the DAG Definition Checkpoint incomplete. The exact disposition set and audit identities are part of the DAG Definition Checkpoint's frozen pre-CAS evidence. A **Complete** Terminal Outcome is evaluated only against those dispositions and evidence bound to the final DAG Definition Index.

## Promotion Candidate identity invariants

A Ticket Base is fixed for one candidate lineage and its review. A review result is promotable only when all delivery bytes descend from that Ticket Base, preserve its bound DAG Definition Index, path set, and content identities, exclude transient run state, and have gates and a Candidate Review Record naming the same final candidate.

Parallel work can make a Ticket Base obsolete before promotion. Silently retaining the old Ticket Base would review accepted changes from other Tickets as though they belonged to the current Ticket; silently changing it would break the recorded identity. The Coordinator Agent instead issues a new Ticket Base equal to the current Accepted Integration Tip. The same Ticket ownership then reapplies its delivery change, reruns invalidated gates, and obtains a new Candidate Review Record. The old record remains provenance, not promotion evidence.

The DAG Integration Branch is kept as a local ref that is not checked out in any worktree. An **Integration Transition** records its candidate kind, exact Base, and reviewed candidate commit/tree; the candidate kind is either Promotion Candidate or DAG Definition Checkpoint. Each Integration Transition verifies that its candidate commit descends from Base, then atomically compares and swaps the DAG Integration Branch ref from that Base to that candidate commit and reads it back. This rules out merge-generated or amended bytes that were never reviewed and avoids moving a ref behind a checked-out worktree. Integration Transitions are serialized even when implementation is parallel, which keeps acceptance order and downstream Ticket Bases deterministic. The Coordinator Agent revalidates the graph, Integration Transition evidence, and Base before starting the Integration Transition, then holds them fixed through local promotion, any selected remote synchronization, and completion. Later graph evidence is processed afterward, avoiding a rollback protocol for an already promoted candidate commit.

Ticket and DAG Milestone describe different surfaces. A Ticket is the semantic acceptance unit; a DAG Milestone is the exact Git commit/tree produced only when that Ticket's non-empty Promotion Candidate completes its Integration Transition and becomes the new Accepted Integration Tip. A DAG Definition Checkpoint may also advance the Accepted Integration Tip and downstream Ticket Base, but it accepts no Ticket and is not a DAG Milestone. Promotion Candidate history before promotion is implementation evidence, not a DAG Milestone. Baseline Satisfaction and Superseded Ticket transitions may change graph state without moving the Accepted Integration Tip, so they create no new DAG Milestone.

## Acceptance and integration publication

Accepted is a semantic result, not a synonym for committed or Ready for Acceptance. The normal evidence path is a reviewed Promotion Candidate promoted with exact identity. A zero-diff Ticket is a different successful path only when the Target Project already defines its Baseline Satisfaction contract and all required evidence is present. Its Ticket Base identity is serialized against Integration Transitions and rechecked so parallel promotion cannot make the audit stale. Otherwise it needs an explicit current-state audit or acceptance decision; manufacturing an empty commit would create form without evidence.

Publication is resolved once before the first Ticket claim. Local-only keeps the Accepted Integration Tip in the local repository. Remote-mirrored selects one configured Git remote and one dedicated remote integration branch, with run-level authority to create that branch and update it after each DAG Milestone or DAG Definition Checkpoint. The local branch name is the default remote branch name. An explicit synchronization instruction is enough when the mapping is unambiguous; configured remotes without a stated intent require one mode decision. No configured remote and no synchronization requirement selects Local-only without a question. Required synchronization without a configured remote requires the user to supply its name and URL and authorize `git remote add` before work begins. This is a branch synchronization choice, not a second release protocol.

Remote-mirrored initialization starts only after the local DAG Definition bytes are verified and live evidence proves the mapping is new; an absent remote ref permits creation, an observed ancestor permits ordinary fast-forward, and exact equality with the locally verified DAG Integration Branch tip completes initial publication and establishes the first Accepted Integration Tip. Once a mapping is established, an absent ref is drift. Established mappings reconcile the Integration Transition's recorded candidate commit, last synchronized commit, and observed remote SHA: candidate equality completes synchronization, last-synchronized equality permits one ordinary fast-forward push, and every other identity blocks. This separation safely handles unsent pushes and lost responses without force-push, ref switching, retry counters, or remote Ticket-branch churn.

## Progress without retry states

A fixed retry allowance is both too strict for difficult Tickets and too permissive for a loop doing the same ineffective work. A diagnostic attempt may eliminate a hypothesis without changing a Promotion Candidate or making a test pass. The execution rule therefore distinguishes an exhausted action from an exhausted path: stop repeating an unchanged failing action and use the evidence to choose another authorized diagnostic or repair path when one remains.

This keeps diagnosis and repair within the Ticket. A non-success Execution Outcome still requires evidence of its actual decision or unavailable external condition; one unsuccessful cycle alone establishes neither. No scheduler-level continuation state or fixed retry allowance is needed.

The graph changes only when the evidence changes a graph boundary: a prerequisite is missing, an edge is wrong, an Acceptance Obligation belongs to another Ticket, or the work has multiple independently acceptable results. Promotion Candidate count, diff size, and review count provide no such evidence.

## Recovery model

The Skill deliberately avoids a separate scheduler database. The DAG Definition Index and repository state establish the recoverable graph, while a compact Run Receipt indexes the Accepted Integration Tip, exact DAG Definition identities, any typed pending Integration Transition with its frozen evidence, claims, Execution Outcomes, and closing conditions. The receipt lives outside delivery history: committing run state after review would create an unreviewed descendant and make the next Ticket Base ambiguous.

Recovery first resolves writer ownership. If liveness is uncertain, the existing claim and workspace remain untouched until the task is contacted, an acknowledged stop is obtained, or an authorized host-level termination establishes quiescence. The closing condition has an owner and a concrete recheck event, so “unknown” cannot silently become a duplicate writer or an unbounded retry loop. If the Agent must change, first confirm that the original Agent has stopped, then give the original Ticket, branch, worktree, and WIP to the replacement Agent.

Graph replacement uses the same boundary. Before a Ticket enters an active Integration Transition, it becomes a Superseded Ticket and closes its claim only after its writer is stopped and evidence is preserved; replacement work cannot begin while the old writer may still mutate the workspace. Once the Integration Transition begins, the Ticket finishes local promotion, any selected remote synchronization, and Accepted under the graph and evidence checked at entry. Evidence arriving later participates in the next graph recomputation.

An unresolved `Needs Decision` Execution Outcome is itself a live progression path, so it prevents a **Stalled** Terminal Outcome. The Coordinator Agent resolves it within existing authority or asks the user; only after the choice is made may any remaining unavailable condition be represented as an owned external block and participate in the whole-DAG terminal check.

## Runtime dependency bootstrap

The Execution Agent depends on one pinned Runtime Skill Bundle: `tdd`, `codebase-design`, and `code-review`. Bootstrap is keyed by Agent Host, stable Skills root, and pinned revision/tree identities. A missing or mismatched member is a recoverable Agent Host condition, not a reason to claim a Ticket that cannot finish its contract. The Coordinator Agent therefore runs the bundled installer by default before the first claim whenever that bootstrap identity cannot resolve the complete pinned bundle.

The installer is deterministic and conflict-safe: it reuses exact pinned Runtime Skill trees, creates missing directories, and refuses to replace any different existing target. The matching `setup-matt-pocock-skills` helper is not a runtime dependency. An explicit installation request or an authorized configuration task that requires this helper triggers its installation with `--include-setup-helper`. The Coordinator Agent carries out that prerequisite under existing authorization; the user does not need to know the installer flag or approve the same work twice. A request to install the helper alone does not authorize project configuration.

Installation completion and runtime readiness are separate checks. After file installation, the Agent Host reloads its Skill list and must resolve all three Runtime Skills. Startup does not run a real review or another Skill workflow as a probe. An Agent Host reload requirement, unresolved Skills root, incompatible existing target, unavailable Python/Git/network, or denied write leaves the Ticket unclaimed with one observable closing condition. This prevents a successful copy from being mistaken for an active capability.

Runtime Skill invocations also need the Target Project's authoritative context. The fixed Ticket contract provides the Ticket, Spec, and candidate identities; the project's existing tracker workflow supplies source-discovery instructions, whether stored at a dependency's conventional path or supplied elsewhere. Project instructions govern that choice. Existing approvals remain valid within their scope, and missing context is resolved as a specific gap. This keeps setup optional without changing the dependency's review process or granting configuration authority.

Each DAG start or resume performs this check once. After it succeeds, every Ticket in that run uses the same verified bundle without another preflight; the installer is not part of the per-Ticket loop. A later start or resume checks again and installs only when a Runtime Skill is missing or its pinned identity no longer matches.

## Compatibility boundary

The copyable artifact is [`skill/dag/`](../skill/dag/). Its references are disclosed by runtime branch, [`validate_definition_index.py`](../skill/dag/scripts/validate_definition_index.py) validates Definition identity without reading working-tree bytes, and [`install_runtime_skills.py`](../skill/dag/scripts/install_runtime_skills.py) recovers a missing Runtime Skill Bundle. Both helpers stay small and stateless; validated Git evidence and active capabilities, rather than command exit alone, form the claim gate.

Delivery is intentionally Git-backed because the required `code-review` contract pins a Git fixed point, non-empty diff, candidate commit list, and `HEAD`. The Skill does not claim an equivalent non-Git review or promotion path.

The project intentionally adds no scheduler service, workflow DSL, model-profile negotiation layer, or compatibility state machine. Those mechanisms would add change surfaces without solving a demonstrated graph problem.
